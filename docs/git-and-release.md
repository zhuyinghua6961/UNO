## 为什么不能直接把目录当分支

普通 Git 分支描述整个仓库的快照，不是单个文件夹的版本。建议同一 monorepo 快照始终保留 backend/web/flutter/deploy，这样一次跨端协议修改可以对应同一版本。

如果三个分支用于开发/测试/生产，各分支应保留完整目录结构，通过合并推广版本，不将不同端分别删到只剩一个文件夹。

如果确实要求三个端分别在三个既有分支工作，需先查看该大仓库实际组织方式，再选择独立 worktree 检出和集成策略。worktree 是同一仓库的不同完整检出，不在三个业务目录内擅自 git init 伪造绑定；也不能以空目录覆盖远程原有文件。

## 获取信息后的操作顺序

检查远程及三个分支 → 确认项目子路径和已有代码 → 比较现有骨架 → 明确跨端协议合并方式 → 再按授权关联。默认不强推、不覆盖历史、不自行提交。

## 发布约定

release 目录存实际产物，默认忽略二进制；发布清单记录版本、构建时间、源码提交（若存在）、脏工作区标记和校验和。没有提交时源码版本为 null，不伪造 Git 关联。

以后 CI 可按 backend/web/flutter 路径触发对应测试，但一次可安装版本应能追溯到明确的兼容组合。具体 CI 文件需等确认 GitHub/GitLab/其他平台及分支名后再生成。
