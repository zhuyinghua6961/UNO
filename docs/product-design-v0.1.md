# UNO 在线游戏整体设计草案 v0.1

> 已被 `architecture-v0.2.md` 的用户新要求取代：前端改为 Vue，后端改为 Spring Cloud，新增 Flutter App，文字聊天与队友语音进入需求范围。本文件仅保留早期讨论历史，不再作为实现依据。

日期：2026-09-06。状态：需求探索，未经用户确认，不是冻结规格。

## 1. 已确认与暂定假设

已确认：要开发 UNO 玩法的游戏；用户分别登录；目前需求模糊；项目已准备卡牌、按钮、图标与音效素材，尚未实现游戏。

为了便于讨论，以下采用可调整的默认方向：

- 第一批用户是邀请来的朋友，而不是陌生人竞技社区。
- 第一版是浏览器游戏，电脑优先、手机可用；暂不开发原生 App 或微信小程序。
- 每桌暂支持 2–6 人。这是本产品的第一版限制，不是 UNO 官方人数限制。
- 先完成一个回合决胜的好友房；暂不做累计 500 分的多回合赛制。
- 用户通过邮箱与密码注册登录，昵称用于展示；昵称不是登录身份。
- 不涉及付费、筹码交易、兑换、下注。

优先确认的不是技术框架，而是：第一批玩家是谁、在哪里打开游戏、怎么找到同桌的人。

## 2. 产品目标与核心流程

目标：玩家能方便地邀请朋友，稳定打完一局，在刷新或短暂断网后回到原来的牌桌。

流程：邀请链接/首页 → 注册或登录 → 大厅 → 创建或加入房间 → 准备 → 对局 → 结算 → 再来一局。

邀请链接在登录过程中保留，登录成功后回到受邀房间；房间已关闭或已满时说明原因并返回大厅。

账号的价值：固定身份、断线后认回原座位、保存偏好和战绩。不要只为了增加一道登录页面而做账号。

## 3. 第一版范围

| 领域 | 第一版必须完成 | 以后再考虑 |
| --- | --- | --- |
| 账号 | 注册、登录、退出、邮箱验证、密码找回、昵称、预置头像 | 微信/手机号/第三方登录、上传头像 |
| 大厅 | 创建房间、房间码加入、邀请链接、返回进行中的对局 | 随机匹配、公开房间列表、好友关系 |
| 房间 | 玩家列表、准备、规则展示、房主开始、房主移交 | 观战、复杂权限、比赛房 |
| 对局 | 发牌、轮次、基础牌效、选色、UNO 宣告/抓漏喊、+4 质疑、胜负 | 叠加、抢出、7–0、多种牌组 |
| 稳定性 | 刷新恢复、短时重连、超时策略、重复操作保护 | 跨地区与大规模多机部署 |
| 个人中心 | 头像昵称、音量偏好、近期正常完赛记录 | 段位、排行榜、成就、赛季 |
| 社交与商业 | 固定表情或短语可选，不影响核心交付 | 自由聊天、语音、商城、支付 |

开放注册前不能省略账号恢复与基础防滥用。若仅为内部玩法验证，可使用预建测试账号，但不能把这种方式当作正式注册系统。

## 4. 页面与交互

### 4.1 登录与注册

一个入口切换登录/注册；提供忘记密码；登录时不暴露“邮箱是否存在”等额外信息。账号使用稳定用户 ID，昵称可以修改。

### 4.2 大厅

只突出三件事：创建房间、输入房间码、返回当前房间。入口边上提供玩法说明与个人中心，不用排行榜或促销填满页面。

### 4.3 等待房间

显示房间码、邀请按钮、玩家席位、准备状态和本局规则摘要。至少 2 人且全员准备后，房主可以开始。修改规则或人数上限需要重置准备状态。

房主只是等待房间的管理者，不负责主持游戏计算。等待阶段房主离开时，移交给最早加入的在线玩家；开始后不能踢正在参赛的人。所有人离开后回收房间。

### 4.4 对局桌面

- 下方：自己的手牌，支持横向滚动；可出牌高亮；摸牌与 UNO 操作清晰区分。
- 中央：弃牌堆、摸牌堆、当前有效颜色、方向、轮到谁。
- 上方/两侧：其他人的头像、手牌张数、在线状态，不显示其手牌内容。
- 辅助区：最近几条公开操作、规则入口、音效开关。
- 选择万能牌时，先选颜色再一次性提交，取消选择不会改变服务端状态。
- 出牌失败时显示明确原因，不静默吞掉操作。

手机优先保证手牌可点击、选色不遮住操作、轮到自己足够明显。颜色需配合文字或符号，不只依赖颜色。

### 4.5 结算与个人中心

结算显示赢家、参与者、本局时长，并提供再来一局与返回大厅。单轮玩法只确定赢家，不虚构其他人的官方名次。正常完赛计入个人战绩；中断对局单独记录，不混入胜率。

## 5. 玩法基线与线上约定

经典基线参考 Mattel 说明书 [1]：同色/同数字/同符号出牌，摸牌规则、功能牌、UNO 漏喊处罚、+4 质疑。默认关闭叠加、抢出和 7–0。两人局反转等特殊规则需要专门测试。

第一版选择单轮胜负，底层保留规则版本，便于以后增加多轮计分。108 张基础牌与现有素材索引对应，重复牌共用一张美术，但每张逻辑牌有独立 ID。

以下是建议的线上产品规则，不是官方 UNO 规则，数值需要试玩后调整：

| 情况 | 暂定处理 |
| --- | --- |
| 普通回合超时 | 30 秒；尚未摸牌则自动摸 1 张后结束，已经摸过则直接结束，绝不因为重试多摸 |
| +4 质疑 | 给受影响玩家 8 秒选择接受/质疑，期间不推进普通回合；超时视为接受 |
| 短暂断线 | 保留席位 60 秒，回合计时继续运行，允许重连 |
| 断线超过保留期或主动退出 | 第一版终止本局，标记中断、不计胜负；其他玩家回等待房间 |
| 连续 3 次普通回合超时 | 提示后中断本局；暂不实现机器人接管 |
| 服务端重启 | 第一版将未完成局标记为系统中断，不假称能跨进程恢复 |
| 同一账号多个页面/设备 | 每局只允许一个有效操作连接，新连接接管后旧连接停止操作 |

中断策略适用于小范围好友测试，不适合直接用于竞技排位。若需要陌生人匹配，应先实现托管/弃权与防刷分设计。

+4 出牌前应记录用于质疑判断的当时手牌与有效颜色；不能用后续状态重新判定。普通客户端看不到其他人的手牌，质疑如需展示证据，只能定向给规则允许的质疑者。

UNO 宣告与抓漏喊的窗口、摸牌后继续出牌、末张功能牌的罚牌结算、弃牌堆重洗，都要在规则模块中显式建模，不要藏在动画回调里。

## 6. 架构建议

采用一个代码仓库、前后端职责分离、一个后端进程的模块化设计。先不拆微服务，不引入多机分布式房间。

暂定技术组合：React + TypeScript 界面、Node.js + TypeScript 后端、Socket.IO 实时通信、PostgreSQL 持久化。框架和具体版本在开始实现时再确认和锁定。

浏览器通过普通请求完成账号、资料、历史记录查询；通过实时连接提交准备、出牌、摸牌等指令，并接收状态更新。Socket.IO 的双向通信和连接恢复能力可作为基础，但连接恢复并不保证成功，仍需完整状态同步的兜底 [2][3]。

### 6.1 模块划分

| Module（模块） | 负责 | 不负责 |
| --- | --- | --- |
| Identity | 用户、会话、登录、恢复、账号权限 | 判断一张牌能否打出 |
| Rooms | 房间成员、准备、房主、邀请、生命周期 | 发牌与胜负判断 |
| Game Engine | 牌堆、回合、规则、动作校验、罚牌、胜负 | 网络、数据库、页面与动画 |
| Match Runtime | 按顺序接收指令、服务器计时、连接状态、调用规则模块、分发视图 | 另写一套玩法规则 |
| Match History | 正常完赛/中断记录、历史查询、可重算统计 | 接受客户端提交的获胜结果 |
| Assets & UI | 素材映射、动画、音效、用户操作反馈 | 决定真实游戏结果 |

规则模块提供少量稳定 Interface：创建初始局面、应用动作、生成某玩家可见视图。实现内部可以复杂，但调用者不应自己处理各种罚牌分支。

随机源和时间作为可控制的依赖传入，便于测试；生产洗牌使用服务端安全随机源。不要提前设计未使用的引擎适配层。

### 6.2 服务端裁决与同步

- 客户端只表达“我要打出这张牌”，不能直接声明“已合法出牌/我赢了”。
- 服务端逐条验证用户身份、所属对局、轮次、卡牌归属和规则，再更新局面。
- 每条指令有唯一 ID 和预期状态版本；重复指令返回已有结果，过期指令要求重新同步。
- 同一对局串行处理，保证两个并发动作不会同时成功改变同一轮次。
- 每个玩家接收单独生成的可见视图；绝不先发全量手牌再靠界面隐藏。
- 连接建立、重连和敏感操作均检查有效会话；过期或退出登录后撤销操作权限 [4][5]。
- 重连成功后按最新权限重建视图；不能把“TCP/Socket 重连了”当作“玩家已回到正确局面” [3]。

## 7. 数据设计

先保留五类持久数据，不把所有临时对象都变成数据库表：

| 数据 | 核心内容 |
| --- | --- |
| users | 用户 ID、规范化邮箱、密码哈希、昵称、预置头像、账号状态 |
| sessions | 会话令牌摘要、用户 ID、有效期、撤销状态 |
| account_tokens | 验证/密码重置令牌摘要、用途、过期时间、是否使用 |
| matches | 对局 ID、规则版本、起止时间、正常完成/中断状态、赢家 |
| match_players | 对局与用户关联、座位、完赛结果、退出状态 |

活动房间、牌堆、手牌和回合时钟先在单进程内存维护；账号会话和历史进入数据库。创建对局时写入进行中记录，进程重启时将遗留记录标记为系统中断。

结算在事务内完成，使用唯一约束避免重复计入战绩；统计初期从正常完赛记录查询，或通过可重建汇总生成。诊断日志默认不记录密码、令牌或完整手牌。

想支持服务端重启后继续对局时，再增加受保护的快照与动作日志；想支持多个进程时，再设计房间归属、共享状态与故障恢复。Redis 不是第一版的默认前置条件。

## 8. 账号与安全底线

- 密码不以明文或普通快速哈希保存，使用成熟实现的 Argon2id 等密码哈希方案 [6]。
- 推荐同站点部署，使用服务端可撤销会话与 HttpOnly / Secure Cookie，并配置 SameSite 和适当的请求防护 [4]。
- 实时连接校验 Origin、身份和消息内容；限制消息大小、频率以及房间加入尝试 [5]。
- 房间码使用随机值、避免顺序可猜、限制暴力尝试；房间码不能代替账号认证。
- 自由输入文本做长度限制和安全展示；第一版先不开放头像上传、自由聊天，减少额外风险。
- 管理员不是另一类游戏玩家。邀请内测只需最小运维能力；公开注册前补充封禁、滥用处理、数据管理与必要的使用说明，不急着做完整后台界面。
- 正式命名与发布前单独核对 UNO 品牌和素材使用；已有第三方素材不等于官方授权。

## 9. 实施顺序与验收

### 阶段 A：确认方向与可点击原型

确定用户、平台、登录方式、模式和美术方向。做大厅、等待房间、牌桌、结算的可点击原型。验收：玩家知道如何加入、准备、出牌、再来一局；本阶段不宣称多人联网已完成。

### 阶段 B：玩法与本地多人技术验证

先测试独立规则模块，再用两个或更多测试身份连接同一后端完成一局。验证方向、罚牌、UNO、+4 质疑、摸牌后动作、重洗、胜负与私有视图。测试身份只用于开发，不替代下一阶段认证。

### 阶段 C：完整好友房最小版本

加入真实账号、邀请流程、准备、重连、服务器计时、幂等操作和历史记录。验收：2–6 个独立账号能正常完赛、刷新恢复、再来一局，不能看见或操作他人手牌。

### 阶段 D：部署与小范围试玩

配置 HTTPS、邮件发送、数据库备份、错误监控和发布流程。测试手机、弱网、断网、重复点击、同账号双开、会话撤销和服务器重启。正式邀请之前通过账号隔离与非法动作测试。

暂定负载验证目标是 10 个同时进行的 6 人房间（60 个活跃连接），不是已验证容量或上线承诺；压测记录延迟、错误率、内存增长后再决定容量。

完成一个阶段再细化下一阶段，不先承诺固定工期。工期与部署费用取决于平台、登录渠道、发布地区、并发目标和现有基础设施。

## 10. 暂不决定与下一步问题

优先问题：第一批玩家是谁，他们通常怎样约到一起玩？

随后确认：是否必须微信内打开、是否需要陌生人匹配、是否要机器人、偏休闲还是竞技、是否公开发布、预期并发与部署地区。当前文档中的默认值应随这些答案更新。
