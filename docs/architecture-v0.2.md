## 2. 产品模式建议（待确认）

### 经典自由局

暂定 2–6 人，各自为战，默认经典牌效和单局胜负；有房间文字，没有队伍文字/队友语音。

### 四人 2v2

将“两人组队”暂解释为四位真人、每队两人，座位交替 A1 / B1 / A2 / B2。不是两人对战，也不是已经确定的双人合作打机器人。

建议首版胜利规则：任意队员率先出完手牌，整队获胜；每人仍持有独立手牌，不共享、不交换，不自动看见队友手牌。正常牌效仍作用于出牌顺序中的玩家，不能任意指定目标。该模式是产品变体，需单独展示并确认，不宣称它是经典官方默认规则。

开始前选择队伍，2+2 齐备且全员准备后才能开局；开局后禁止换队。文字允许向房间或队伍发送，语音只在同队之间传输。通过沟通口述手牌可作为允许的配合方式，但软件不泄露任何玩家的私有手牌数据。

## 3. 页面设计

两端一致的主要入口：登录/注册 → 大厅 → 等待房间 → 牌桌 → 结算 → 再来一局；个人中心保存资料、偏好与记录。

大厅展示模式、创建/加入、返回进行中对局。等待房间展示邀请码、队伍席位、准备、规则与语音状态。牌桌展示自己的手牌、对手牌数、当前颜色/方向、回合时限、摸牌、UNO、聊天抽屉和麦克风入口。

Web 预览已提供大厅、牌桌、账号占位；Flutter 预览提供对应页面。创建房间、登录、发送消息、语音按钮尚未开放。不能用演示数据营造已经联机的假象。

## 4. 后端部署拓扑

```text
Vue 浏览器 / Flutter App
  ├── HTTPS：账号、房间、历史 → Spring Cloud Gateway
  ├── WSS：对局指令/状态、文字 → Gateway → game-service（计划）
  └── WebRTC：音频媒体 → LiveKit（计划），不穿过 Java 对局广播

Gateway
  ├── identity-service：身份、会话、资料（当前只提供状态接口）
  └── game-service：房间、规则调度、消息、语音准入（当前只提供状态接口）
        └── game-core：纯 Java 规则及权限策略，独立测试

PostgreSQL：已接入双服务独立数据库与迁移；已建账号/凭证基础表，对局/战绩/文字表尚未实现
Redis：会话、限流、在线状态、后续跨实例协调（尚未连接）
LiveKit：每场对局每队独立音频房间（只有可选部署配置，尚未集成）
```

先拆网关、账号和对局三个进程，不急着把房间、聊天、战绩分别拆成微服务。聊天策略与对局成员关系强相关，初期放在 game-service 内便于一致校验。后续确有规模压力再拆分。

Spring Cloud 当前使用 BOM 与 Gateway；尚未接 Nacos/Eureka、配置中心、服务治理与熔断。开发环境使用 Docker DNS / 环境变量路由，不为了凑技术名词引入全套平台。

## 5. 账号方案建议

Web 建议采用同站 HttpOnly/Secure Cookie 会话；Flutter 使用短期访问凭证和轮换刷新凭证，刷新凭证进入系统安全存储。两种入口最终对应同一 userId，不要求把浏览器凭证放入 localStorage。

登录渠道待确认，先为邮箱+密码预留；正式开放前完成密码哈希、验证/找回、登录限流、会话撤销和设备管理。网关可以做第一道过滤，但账号服务和对局服务仍需验证身份，不能仅信任客户端传来的 userId 或随意设置的请求头。

当前没有账号存储或登录逻辑；Spring Security 对未实现的受保护路径拒绝访问，不存在默认测试账号。

## 6. 实时对局与文字聊天

采用标准 WebSocket + 版本化 JSON 协议，不使用 Socket.IO 协议，从而让 Spring 与 Flutter/Web 使用一致协议。

对局指令由服务器裁决。客户端提交 commandId、matchId、expectedVersion 和动作内容；服务器按对局串行处理、校验身份与轮次、幂等去重，再分别生成玩家视图。重连根据服务端状态恢复，不接受客户端上传手牌作为真相。

文字分 ROOM / TEAM 两类；频道名称或 teamId 不能作为授权依据，服务端从实时房间席位重新计算接收者。服务器生成发送者身份、messageId、时间、递增消息序号。每次发送与拉取历史都重新校验范围。

建议限制：单条最多 500 个 Unicode 码点、纯文本展示、基础频率上限 2 条/秒与短时突发限制；客户端不能通过 HTML 渲染消息。服务端限流、持久化、历史补偿与举报尚未实现。已有 ChatMessage 仅完成内容约束，不是完整过滤与审核系统。

待补数据：room、room_members、match、match_players、match_teams、chat_messages、session 与 account_tokens。聊天历史保存时长与用户删除策略在公开上线前确认，默认不永久保存。

## 7. 队友语音

### 交互

- 玩家主动点击“加入队友语音”后申请麦克风权限；不因进入房间而自动录音。
- 支持自己静音/开麦、退出语音、麦克风被拒绝提示、队友正在说话状态。
- 首版建议只做前台语音，退到后台时明确暂停；后台保活、蓝牙切换和音频焦点作为后续专项。
- 不录音，不接摄像头，不提供全房间语音；音频不进入文本日志。

“直接开麦”表示操作简单，不表示绕过浏览器/手机权限。Web 公网环境需要 HTTPS，App 需要平台权限声明和运行时授权。

### 实现与隔离

建议 LiveKit 作为 WebRTC 音频基础设施，Web 接 JS SDK，Flutter 接 Flutter SDK。当前没有安装这两端 SDK 或实现令牌端点。

令牌请求只传对局 ID；后端从有效会话和服务器维护的席位计算队伍，不接受客户端自报 userId、teamId 或 roomName。凭证只允许指定音频房间、身份和麦克风发布，禁止视频、屏幕共享、任意建房、管理权限和数据发布；文本仍走游戏通道。

A 队、B 队必须是不同的 LiveKit room，不能把四人放同一个房间再靠前端静音隐藏对手。房间名包含对局/成员代次，每次成员或队伍变更都更新代次。

令牌短时有效并不等于已建立连接自动到期。退出、封禁、结束需要服务端移除媒体成员、终止房间；自托管 LiveKit 的旧令牌还可能在过期前再次使用。因此代次变更后让有效队员迁移新媒体房间，旧令牌无法进入承载新音频的房间；不能只依赖一次踢人或客户端 disconnect。此撤销流程需要集成与对抗测试，当前未实现。

语音故障不阻塞对局；即使麦克风被拒绝、TURN 不通或队友断线，文字与出牌仍应可用。

## 8. Docker 和发布

Compose 默认启动 Web + Gateway + Identity + Game + PostgreSQL。infrastructure profile 可额外启动 Redis；voice profile 可启动 LiveKit，但不会因此让应用自动获得聊天或开麦功能。数据库结构、运行配置与迁移规范见 [stage2 数据库指南](persistence.md)。

现有 LiveKit 配置是仅本机验证用途，广告地址 127.0.0.1；不能用于手机实机或公网。生产必须另行配置域名、TLS、可达媒体地址、UDP/TCP、TURN/TLS、防火墙、容量与监控。Nginx 的 HTTP 代理不能代替 WebRTC 媒体端口。

release 保存 Web 静态资源、后端 JAR、后续 APK/AAB/IPA、校验和及 manifest；源码与制品分离。发布脚本当前只归档已构建的 Web/JAR，不承诺离线 Docker 安装或完整产品发布。

## 9. 优先级与验收

以下 P0–P4 是高层概览；具体执行拆分、依赖和完成状态以 [stage1–stage18 总索引](README.md) 为准。

| 阶段 | 工作 | 完成标准 |
| --- | --- | --- |
| P0 当前骨架 | 三端目录、可编译入口、状态接口、通信权限基础、Docker、协议文档 | 构建/测试通过，明确标记未接入功能 |
| P1 账号与等待房间 | 确认登录渠道、真实账号、会话、邀请、2v2 组队准备 | 两端不同用户可以进入同一房间，不能冒充别人 |
| P2 完整规则与文字 | 发牌、基础牌效、UNO/+4 质疑、2v2 结算、文字、重连 | 四人打完一局，队伍文字不泄露，重复动作不生效 |
| P3 队友语音 | LiveKit 令牌端点、双端 SDK、权限、静音、退房撤销 | 队友能互听，对手不能听；拒绝麦克风不影响游戏 |
| P4 小范围发布 | 生产域名/TLS/TURN、移动端签名、备份监控、负载与弱网测试 | 跨 Web/App 完赛、重连、消息补偿、语音撤销均验收 |

先保证聊天/对局单实例正确，再考虑多实例。关键测试：伪造队伍、旁观者偷听、重连后旧队凭证、双设备抢同一席位、退出后发消息、跨队消息历史、麦克风拒绝和弱网回退。
